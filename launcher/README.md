# launcher

**Status: shipped, tested on every platform, not yet the plugin's start command.** The manifests the plugin ships (`.claude-plugin/plugin.json`, `hooks/hooks.json`) still run `node ${CLAUDE_PLUGIN_ROOT}/bin/mm3.mjs mcp` and `node ${CLAUDE_PLUGIN_ROOT}/hooks/nudge.mjs`, exactly as before the launcher existed, so no plugin user's start-up changes. The launcher-form manifests are kept as data in `launcher/manifests/` (`plugin.json`, `hooks.json`); the launcher tests, the real-Claude-Code test and the CI launcher jobs install those into a plugin copy. **The switch** (a later release) is a copy plus one constant: `cp launcher/manifests/plugin.json .claude-plugin/plugin.json && cp launcher/manifests/hooks.json hooks/hooks.json`, set `LAUNCHER_WIRED_INTO_PLUGIN = true` in `test/helpers/launcher.ts`, then regenerate the pin (`npm run gen:checksums`: the standalone embeds both manifests, so its hashes change). `test/unit/launcher-manifests.test.ts` fails on a half switch either way. Everything below describes the launcher and what the plugin does after the switch.

`mm3-launch` is then the one command the Claude Code plugin runs (`.claude-plugin/plugin.json` for the MCP server, `hooks/hooks.json` for the hooks). The command is the same on every OS, `${CLAUDE_PLUGIN_ROOT}/launcher/mm3-launch`, with no extension and no `sh` in front:

- **macOS and Linux** run that file (POSIX sh) directly: shebang `#!/bin/sh`, execute bit kept in git.
- **Windows** starts the MCP command through cmd (proven on GitHub: with Git for Windows' default `PATH`, which has no `sh`, a manifest command of `sh ...` fails with `'sh' is not recognized`). cmd adds the extensions in `PATHEXT` to a command that has none, so it runs `mm3-launch.cmd` next to it, the same way npm's `node_modules/.bin/<tool>` runs `<tool>.cmd`. The batch file needs only cmd when Node is usable.
- **Hooks** are shell-form commands (`"${CLAUDE_PLUGIN_ROOT}/launcher/mm3-launch" hook`): Claude Code runs them with `sh -c` on macOS/Linux and in Git Bash on Windows, which finds `sh` itself. An exec-form hook cannot do it: on Windows it needs a real `.exe`. A Windows machine with no Git Bash at all (Claude Code then uses PowerShell for hooks) gets a hook error on its hooks, not on the MCP server.

- **Node 22.13 or newer is there:** it starts MM3 exactly as before (`node bin/mm3.mjs mcp`, `node hooks/nudge.mjs`). Nothing is downloaded.
- **Node is missing, older, or MM3 will not start on it:** it downloads the self-contained MM3 for this machine once, from this repository's GitHub Release for the plugin's own version, checks it against the sha256 pinned in `checksums.json`, installs it (`mm3 init --no-claude --no-key --yes`), and runs it. A file that does not match the hash is deleted and never run. Later starts download nothing.

Files: `manifests/plugin.json` and `manifests/hooks.json` (the launcher-form manifests, data), `mm3-launch` (POSIX sh: Linux, macOS, and the hooks on Windows through Git Bash), `mm3-launch.cmd` (the Windows MCP entry: checks `node --version` against the floor, probes `node bin\mm3.mjs --version`, runs `node bin\mm3.mjs mcp`, else calls the PowerShell step; CRLF line endings are required, see `.gitattributes`), `mm3-launch.ps1` (the Windows download step), `checksums.json` (generated by `npm run gen:checksums` from the build, never edited by hand; `npm run check:launcher` checks it).

Six builds, named `mm3-<version>-<os>-<cpu>` (`.exe` on Windows): `linux-x64`, `linux-arm64`, `win-x64`, `win-arm64`, `darwin-arm64`, `darwin-x64`. The sh launcher turns `uname -s` / `uname -m` into that key; the PowerShell one uses the machine's CPU (`OSArchitecture`, else `PROCESSOR_ARCHITECTURE`). A machine that maps to no listed key (say Linux on RISC-V) gets one line, `no self-contained MM3 build for <key>`, asking for Node 22.13+. `check:launcher` fails unless all six are pinned and names each missing one with the runner that builds it. No one machine builds all six (the macOS files need a Mac), so the `pin` job of `.github/workflows/standalone.yml` downloads all six builds and, on a mismatch, prints the complete `checksums.json` to commit.

Why a folder of its own: `hooks/` and `.claude-plugin/` are read by agents and by the standalone build (`hooks/` and `.claude-plugin/` are embedded in it), and `checksums.json` records the hash of that build, so it must live outside both.

## Bringing up a Windows change

Windows behaviour (cmd, PATHEXT, Git Bash, PowerShell, paths with spaces) cannot be settled on Linux, and the big matrix (`.github/workflows/standalone.yml`, six builds, every tier) takes long and hides one answer among many. So a Windows-specific change is iterated first on a throwaway branch with the one small workflow `.github/workflows/launcher-windows.yml` (`workflow_dispatch`, the Windows launcher cases only, it builds win-x64 itself and uses nothing from other workflows). Run it from the throwaway branch (GitHub lists a `workflow_dispatch` workflow once the file is on the repository's default branch) until `cmd-default` is green, then bring the change to the feature branch and let the big matrix confirm it. The big matrix is never the place to guess.

In the big matrix every launcher job is informational (the launcher is not the plugin's start command yet), and `.github/workflows/standalone.yml` says which jobs gate.
